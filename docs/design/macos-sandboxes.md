# Design: macOS sandboxes and a second template (agreed, not started)

**Goal:** keep developing Bergfried itself inside a sandbox. The Go parts build and test on Linux, but the SwiftUI app needs a macOS toolchain (`swiftc`, macOS SDK, `codesign`). So Bergfried gets a second VM template with a **macOS guest** next to the current Linux one.

## Decisions
- **No Docker in macOS guests.** Go is installed natively (Homebrew); the Makefile gets a mode without Docker (for example `make test GO=local`; `make proto` needs `brew install protobuf` plus the Go plugins). Linux sandboxes keep using Docker.
- **`sudo` in macOS guests:** Bergfried reads the guest user's password from `~/password` (generated by Lima) and passes it to `sudo -S` **over stdin** — never on a command line, never logged. Where possible the root-owned pieces (ssh hook config) are installed once while building the base VM (Lima provisioning runs as root), so no `sudo` is needed at runtime.
- **macOS support is labelled experimental** in the app until the checks in step 0 are done.

## What is verified (Lima documentation, read on 2026-11-09)
- Lima ≥ 2.1 runs macOS guests (experimental); the host must be Apple silicon and the same or a newer macOS than the guest; `vmType: vz` only; templates `macos-15|26|27` ship with Lima 2.3 (checked locally).
- Password login is enabled; password-less `sudo` is disabled (except `/sbin/shutdown -h now`, not configurable).
- No automatic port forwarding (use `ssh -L` or the vzNAT address), no containerd, the video display cannot be turned off, no custom CA certificates. First-login screens can be suppressed (`osOpts.Darwin.suppressFirstLoginSetup`, Lima ≥ 2.3).
- **Not found in the docs → untested:** reverse `guestSocket` forwards on macOS guests, `limactl clone` for macOS guests (and its duration), base VM disk size (the restore image alone is ~20 GB). Apple's licence limits the host to **two running macOS VMs**.

## What has to change (Linux assumptions in Bergfried)
| Area | Linux today | macOS guest |
|---|---|---|
| Daemon socket path | `/run/user/<uid>/bergfried.sock` | `/run/user` does not exist → configurable socket directory (template variable, `bergfried-mcp`, ssh config) |
| First boot | `systemd-machine-id-setup`, `dpkg-reconfigure openssh-server`, `systemctl restart ssh` | no equivalent; own script (ssh host keys, hostname) |
| Root-owned files | `sudo install …`, `/etc/ssh/ssh_config.d/*` | `sudo -S` with the password from `~/password`, or install once at base-VM build time; check that `ssh_config.d` + `Match exec` work |
| Packages | `apt-get`, Docker, tmux | Homebrew (`tmux`, `git`, `go`), Command Line Tools |
| `bergfried-mcp` | linux/arm64 | darwin/arm64 too (app bundle ships both; `InstallMCP` picks by guest OS) |
| Monitor probe | Linux `ps -t`, `df`, tmux | BSD flags differ → per-OS probe with parsing tests |
| Git credentials | `credential.helper store` | macOS default is `osxkeychain` → set `store` explicitly |
| Web servers | Lima forwards ports to the Mac | not automatic → hint in the app (`ssh -L`) |

## Plan (small, testable steps)
0. **Spike by hand** (`limactl start template:macos`): verify reverse `guestSocket` forward, `limactl clone` (time, disk), `suppressFirstLoginSetup`, `ssh_config.d` + `Match exec`, headless Command Line Tools install, Homebrew + `go`/`tmux`, `claude auth login` + Remote Control, `sudo -S` with `~/password`, BSD `ps`/`df` output. Write the results into this file. **Stop here if reverse sockets or clone do not work.**
1. **OS abstraction without behaviour change:** one small interface in `daemon/internal/sandbox` (socket directory, first boot, install hooks, install packages, monitor probe, guidance) with the current Linux code behind it; tests with a fake runner.
2. **Data model:** `sandboxes.os` (`ALTER TABLE`, default `linux`); base VM names include the OS (existing `bergfried-base-<hash>` stays recognised as Linux); templates `vm/linux.yaml` (today's file) and `vm/macos.yaml`; `CheckTemplate` per OS; API and CLI take `os`.
3. **macOS implementation:** template, first boot, hook install, `sudo -S` helper (stdin only; test that the password never appears in arguments or logs), darwin `bergfried-mcp` in Makefile, CI and the app bundle.
4. **Monitor per OS** with recorded sample outputs as test fixtures.
5. **Developer toolchain in the macOS guest:** headless Command Line Tools, Homebrew, `make … GO=local`, docs.
6. **App:** OS picker in "New sandbox", an "experimental" badge, hints (disk ≥ ~40 GB, at most two macOS VMs, ports via `ssh -L`).
7. **Docs and tests:** `docs/testing/macos.md`, update ARCHITECTURE, SECURITY and DEVELOPMENT.

## Limitations that will get in the way when developing Bergfried inside sandboxes
**macOS guests**
- **Experimental in Lima**; behaviour can change between Lima versions, and a macOS guest cannot be newer than the host (a host update can force a new base VM).
- **At most two running macOS VMs**, ~20 GB restore image plus the disk of every VM; big downloads and long first builds; a template change means a new base VM.
- **A GUI session is part of macOS:** first-login screens, permission prompts (notifications, accessibility) and Gatekeeper dialogs need someone to click; an agent cannot do that headlessly.
- No automatic port forwarding, no Docker, no containerd; `sudo` needs the password.
- Homebrew/Command Line Tools installs are slower and less scriptable than `apt`.

**Developing Bergfried itself**
- **No end-to-end tests with real VMs inside a sandbox:** Lima VMs cannot be started from within a VM (nested virtualisation is not available or not guaranteed). Those tests stay on the Mac. Unit tests, `fakegithub` tests, Go builds and docs work in a Linux sandbox.
- **Host actions stay manual:** installing a build, restarting the daemon, notification permission, taking screenshots. Feedback loop: agent pushes a branch → CI builds (about 2 minutes) → you install it.
- **Signing and notarisation are impossible in a VM** without your Apple Developer account; builds stay ad-hoc signed.
- **`app/build.sh` runs only on macOS:** in a Linux sandbox the app cannot be built (Go can cross-compile the daemon).
- **The app cannot be looked at from inside the VM** except through the VM's own display window (a macOS guest has one; a Linux guest has none).
- **Release trust:** the sandbox token needs `Contents: write` on this repository, and a tag `v*` publishes a release that the updater installs. Before this repository goes into a sandbox token, protect it on GitHub (free for public repos): a ruleset restricting `v*` tags and requiring pull requests for `main`, **no bypass for the token's account**, and a `release` environment with a required reviewer in `release.yml`.
- **Every change to Bergfried's own VM code is risky to try on the same Mac that runs your other sandboxes** (a bug can break your running agents). Test with a separate `BERGFRIED_HOME` and clearly named test sandboxes.
