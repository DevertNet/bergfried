# Manual test: control app (macOS)

```bash
make build            # bin/bergfriedd, bin/bergfried-mcp (Docker)
app/build.sh          # app/build/Bergfried.app (swiftc, ad-hoc signed, binaries + template inside the bundle)
open app/build/Bergfried.app
```

1. **Settings → General → "Install and start daemon"** (runs in the background with a status text) creates a LaunchAgent (`~/Library/LaunchAgents/de.einfach123.bergfried.plist`, `bergfriedd serve --no-dialog`, log `~/.bergfried/daemon.log`). Alternatively run `bergfriedd serve --no-dialog` in a terminal.
2. **Settings → Base VM → "Build now"** (once, a few minutes).
3. **Sandboxes → "New sandbox"** (no runtime choice), then **"+ Claude"** and choose an existing folder, **Start Claude** in a Claude row, sign in per runtime (Claude and/or OpenCode), start/stop the sandbox, delete (warning for unpushed commits, "Delete anyway" after confirmation).
4. **Requests:** allow/deny file and folder requests (large folders need a second confirmation). Every **Deny** opens a small sheet with an optional **note for the assistant**; the note is returned with the denial. SSH and GitHub token sheets have the same note field. The quick Deny action in a macOS notification has no note field; use the Requests tab for that. SSH requests: "Decide …" opens a scrollable sheet with duration (10–60 minutes in 10-minute steps, then 90 minutes, 2, 4, 8 and 24 hours), user, key, host-key confirmation for new hosts and the note (returned with allow and deny). Active grants with countdown, extend, revoke; each grant shows `Task <id>` – that id is what the assistant uses with `release_ssh`.
5. **Audit log:** filter and CSV export (formulas are neutralised). **Diagnostics:** daemon log (every action logs started/done/FAILED), updater log, Lima log per VM; "Copy all".
6. **Menu bar:** shield icon with the number of open requests; file requests can be allowed/denied right there.
7. **Index explanation:** after the daemon starts (first install and after every update) a dialog explains the macOS folder prompts; the index only starts after "Continue".
8. **Notifications** with action buttons. On first start macOS asks for notification permission — answer it before doing anything else with the app.
9. **Restart needed:** after an update, running Claude entries and the OpenCode service show an orange **"Restart needed"** label. Restart them (Claude: menu → **Restart Claude**; OpenCode: **Stop service** then **Start service**) and the label disappears.

## Features worth checking
- **Edit the VM template:** Settings → **Advanced → Template (bergfried.yaml)**. Only what passes `limactl validate` and keeps isolation is saved. A changed template means a new base VM (build once); existing sandboxes are unchanged; older base VMs are removed after a rebuild. File: `~/.bergfried/template/bergfried.yaml`.
- **Use an existing folder:** "New sandbox" → source "Folder" (CLI: `create <name> --import FOLDER`). The folder is **copied** (never mounted) to `~/work/main`: only below your home, never the home itself, never blocked paths; without `.env`/keys/symlinks/`node_modules`/caches; credentials in `.git/config` are stripped. A preview shows files and size first.
- **Overview:** sandboxes are one **alphabetical card list** (no Running/Stopped groups). Each card has the state/actions, metadata, a **Claude** card (installed, signed in, **+ Claude**, and the folder list with Claude state and actions) and an **OpenCode** card (installed, signed in, service running, Start/Stop service, Connect desktop). There are no runtime chips and no separate worktree table. The OpenCode card shows "service running" even without a Claude entry. A stopped sandbox shows "not checked" until it starts. The daemon polls running VMs every 5 s (unstable) or 20 s (all green).
- **Base VM banner:** when no base exists, the banner offers **Build now** and can be dismissed with **×**; building shows the live output.
- **Login:** the sign-in button opens iTerm (if installed, otherwise Terminal) with `claude auth login` or `opencode auth login`. After a Claude login the daemon restarts the running Claude entries (`--continue`); a new OpenCode login is picked up by the service. Claude onboarding prompts are answered with the preselection.
- **OpenCode desktop app:** start the service with **Start service** if needed (this installs OpenCode), then click **Connect desktop** in the OpenCode card. It works without Claude (sandbox-level service). **Start service / Stop service** control it; the state survives a sandbox stop/start. **Connect desktop** is only shown while the service is running. A sheet opens immediately with "Preparing …", then a one-time link on the sandbox port (42xxx), valid for 5 minutes, with Copy and Open in browser. Do not open it in the browser first if you want the desktop app. Errors are shown in the sheet with Try again.
- **Update size:** when a release is available, the sandbox banner, Settings → Updates and the install button show the zip size (e.g. 12.4 MB).
- **Job output:** expanding the live output follows new lines while you are at the bottom; scrolling up pauses it and shows "Jump to latest".
- **Daemon version mismatch:** if the daemon version differs from the app, an orange banner offers **Restart daemon**. This is the first thing to check if windows seem to run the wrong thing (a second, older daemon may still be driving the VM; `pgrep -af bergfriedd` on the Mac).
- **Remote Control is watched and activated:** if Claude is logged in and a running entry has no active RC after ~15–20 s the daemon answers an open "Enable Remote Control?" prompt with `y`, restarts Claude if only a shell runs, or types `/remote-control` when Claude is idle. Max. 3 attempts per entry, then "RC cannot be activated – restart". Everything is in the audit log (`claude.rc_enable`).
- **Claude:** a new sandbox creates the folder `main` **without starting Claude**. **+ Claude** selects an existing folder or opens the browser to create one; no git worktree or branch is created. Each row shows Folder, Claude state and actions: **Start Claude / Stop Claude**, iTerm, and a menu (copy RC link, restart Claude, remove entry). **Durchsuchen …** opens a folder browser: navigate, show hidden folders with a checkbox, create a folder in the current folder, then choose it. Removing stops Claude and keeps the folder and its contents.
- **Claude vs OpenCode:** Start Claude only affects the selected folder; Start/Stop service only affects the sandbox-wide OpenCode service. Both may use the same folder, but not at the same time on the same files.
- **Restart needed:** running Claude entries and the OpenCode service show an orange **"Restart needed"** label when they were started with older instructions (`bergfried.md`) or an older `bergfried-mcp` than the daemon installs now, or when the daemon has no record of their start ("unknown", for example right after updating from a version without this feature). The tooltip names the reason. Nothing restarts automatically. Claude: menu → **Restart Claude** (reinstalls the helper files first); OpenCode: **Stop service**, **Start service**.
- **Migration:** after updating from an older version, old OpenCode TUI windows are ended automatically (their entries become normal Claude folders with Claude stopped); the folders and git history stay. Start Claude in a folder only if you want it.
- **Shell/SSH into the VM:** sandbox row → "Shell / SSH": a normal shell (`limactl shell`) in iTerm/Terminal, "Copy SSH command" (`ssh -F ~/.lima/<vm>/ssh.config lima-<vm>`, also usable for VS Code Remote-SSH), shell, SSH command and sign-in entries for Claude and OpenCode.
- **Language:** the app follows the macOS language (English or German).

## Technical notes
- The app talks HTTP/JSON over `~/.bergfried/app.sock` (0600). `Bergfried --selftest` checks the connection.
- With Command Line Tools only, `@State` is a macro without plugin; the app uses `@Local` (`Local.swift`).
- Notifications need an ad-hoc signed bundle; without an Apple developer certificate macOS may treat them more strictly. The dock badge, bouncing dock icon and the menu bar counter work regardless.
- Assistants never see the UI (CI only compiles it); the maintainer checks layout, dialogs, notification buttons and the menu bar.
